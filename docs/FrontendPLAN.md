Frontend Implementation Plan for Agent
======================================

You are implementing the frontend for **AgenticNetSec v1**, a network forensic agent platform. The frontend must be built with **Next.js + React + Tailwind + shadcn/ui** and should present a professional, minimal, analyst-style interface for uploading PCAPs, tracking asynchronous analysis jobs, viewing structured forensic findings, validating guardrail status, and supporting the final demo presentation.

1\. Project Goal
----------------

Build a frontend that allows a user to:

1.  Submit a PCAP file or pcap\_path for autonomous analysis.
    
2.  Track the analysis job lifecycle through async REST polling.
    
3.  View outputs generated by the backend:
    
    *   job status
        
    *   report JSON
        
    *   report Markdown
        
    *   metrics
        
4.  Review findings in a structured forensic workflow:
    
    *   evidence
        
    *   timeline
        
    *   findings
        
    *   impact
        
    *   recommendations
        
    *   guardrail verification
        
5.  Demonstrate the project clearly for Deliverable 3.
    

The frontend should reflect the backend data flow:

*   POST /api/v1/analysis
    
*   GET /api/v1/analysis/{job\_id}
    
*   GET /api/v1/analysis/{job\_id}/report.json
    
*   GET /api/v1/analysis/{job\_id}/report.md
    
*   GET /api/v1/analysis/{job\_id}/metrics
    

2\. High-Level UI Requirements
------------------------------

The frontend must communicate that the system:

*   ingests PCAPs
    
*   runs autonomously without user step-by-step intervention

5\. Backend Integration Rules
-----------------------------

Assume the backend follows the async-job REST architecture.

### Create analysis job

Use POST /api/v1/analysisSupport:

*   multipart file upload
    
*   pcap\_path submission
    

Expected frontend behavior:

*   on success, extract returned job\_id
    
*   redirect to /analysis/\[jobId\]
    

### Poll job status

Use GET /api/v1/analysis/{job\_id}Polling behavior:

*   every 2–5 seconds while status is queued/running
    
*   stop when completed/failed
    
*   surface errors clearly
    

### Load artifacts

Use:

*   GET /api/v1/analysis/{job\_id}/report.json
    
*   GET /api/v1/analysis/{job\_id}/report.md
    
*   GET /api/v1/analysis/{job\_id}/metrics
    

The frontend should tolerate:

*   delayed artifact availability
    
*   partial completion
    
*   malformed or missing fields
    
*   backend downtime gracefully

11\. Functional Acceptance Criteria
-----------------------------------

The frontend is complete when:

1.  User can submit a PCAP or path from the UI.
    
2.  Submission creates an analysis job and routes to the job page.
    
3.  Job page polls until completion or failure.
    
4.  User can view human-readable report sections.
    
5.  User can view raw JSON/Markdown/metrics outputs.
    
6.  Guardrail verification is visibly represented.
    
7.  Runtime/cost metrics are displayed clearly.
    
8.  UI supports at least:
    
    *   benign case
        
    *   attack case
        
    *   failure/edge case
        
9.  The flow is smooth enough for recorded demo presentation.
    

12\. Engineering Constraints
----------------------------

*   Use TypeScript.
    
*   Use shadcn/ui for consistent components.
    
*   Prefer server-safe architecture, but job polling and artifact fetching can be client-side where appropriate.
    
*   Keep components reusable and presentation-friendly.
    
*   Do not hardcode backend assumptions beyond the documented endpoints.
    
*   Build defensively for missing fields and evolving schema.
    
*   Add mock/sample data helpers if backend is incomplete.
