# Changes - 2026-03-29

## Summary

Today focused on improving the backend PCAP investigation workflow for the Apex / Lynx-style incident scenario, especially the optional AI-guided `tshark` follow-up flow.

## Backend Logic Review

- Reviewed the current PCAP analyzer against the incident requirements:
  - `A` Initial Access
  - `B` Lateral Movement & Discovery
  - `C` Exfiltration
  - `D` Payload Deployment
- Identified important limitations in the current logic:
  - initial-access reasoning is too RDP-centric
  - WinRM ingress is under-detected
  - brute-force style evidence is not modeled well
  - payload deployment logic is biased toward RDP-based spread
  - deep-dive focus host selection is overly anchored to RDP findings

## Sandbox Verification

- Added a lightweight forensic sandbox approach for second-stage verification.
- Added bounded `tshark` execution that complements the existing Scapy-based analyzer instead of replacing it.
- Added Docker-based sandbox assets and helper scripts for local packet verification.

Key files:

- `backend/src/sandbox_verifier.py`
- `backend/sandbox/Dockerfile`
- `backend/sandbox/bin/build-sandbox.sh`
- `backend/sandbox/bin/run-tshark.sh`

## Post-Processing Existing Results

- Added a workflow to enrich existing `scan_results.jsonl` entries without rerunning the base analyzer.
- The enrichment script reads each record's stored PCAP path and runs sandbox verification later.

Key file:

- `backend/scripts/enrich_results_with_sandbox.py`

## AI-Guided tshark Planning

- Implemented a report-driven AI follow-up flow:
  1. reuse or generate a case report
  2. identify weak ABCD sections at campaign level
  3. select only related files
  4. generate compact per-file `tshark` plans
  5. run those plans in the sandbox

- Corrected the design so it no longer runs by naive file order.
- File selection is now based on weak report sections and aggregate result mappings.

Key files:

- `backend/src/verification_planner.py`
- `backend/src/ai_tshark_planner.py`

## OpenRouter Fixes

- Fixed the planner path so explicit `openrouter` planner runs no longer silently fall back to Gemini.
- Fixed OpenRouter response handling:
  - broader text extraction
  - more compatible chat-completions path
- Fixed model override precedence:
  - `--planner-model` now actually overrides the configured default
- Verified that `openai/gpt-4.1-mini` works reliably as the OpenRouter planner model in the current flow.

## Prompt Improvements

- Improved planner prompts to behave more like a constrained tool-using coordinator:
  - explicit sandbox/tool contract
  - allowed field list
  - valid display-filter rules
  - stage-specific investigation guidance for A/B/C/D
  - anti-pattern warnings
  - stronger host anchoring
  - reduced report context for per-file planning

Observed effect:

- planner execution became reliable
- AI-authored queries stopped failing at the same rate as earlier runs
- results improved mainly for targeted `B/D` follow-up on selected files
